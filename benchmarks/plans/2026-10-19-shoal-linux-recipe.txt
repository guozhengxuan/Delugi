Shoal++ native Linux build and fixture recipe — 19 October 2026

Source: aptos-labs/aptos-core paper-shoal, commit 9653e47dc6a08f4bb15e8f138ad79fb2045fccab.
Review status: pinned native Linux ARM64 validator/fixture builds and five local finite-cohort resource/accounting fixtures verified. See benchmarks/results/shoal-native-local-acceptance-2026-10-19.json. Formal performance and observer-cost acceptance remain separate.

Build-host envelope
Use Ubuntu 22.04 with a dedicated scratch directory. The pinned configuration enables SSE4.2/lld only for x86_64; a local ARM64 build retains its native target defaults and must record that distinct ABI. Start with CARGO_BUILD_JOBS=1, CARGO_INCREMENTAL=0. Estimated scratch is 40–100 GiB and peak linker/process memory 16–32 GiB; these are conservative planning estimates, not measured results. A 4-vCPU/16-GiB/200-GiB build host can try jobs=1 with temporary swap. Swap must be disabled on evaluation validators. Prefer an 8-vCPU/32-GiB host if the linker exceeds memory. Record actual peak RSS, disk high-water mark, elapsed time, and any swap during the build. No other large native build should run concurrently.

The helper verifies the exact source commit and recorded instrumentation patch, enforces the reviewed Cargo.lock, uses Rust 1.75.0, disables incremental builds, and explicitly sets CARGO_PROFILE_RELEASE_DEBUG=0. The reviewed lock retains every upstream external package/version/source and adds only the dependency-free local delugi-benchmark-observer crate used by aptos-crypto and aptos-types. Upstream release overflow checks and .cargo/config.toml target-specific rustflags are preserved. The debug-info override changes build disk size, not consensus.
It builds separately:
  cargo +1.75.0 build --release --jobs 1 --locked -p aptos-node --features consensus-only-perf-test
  cargo +1.75.0 build --release --jobs 1 --locked -p aptos-genesis --bin shoal-fixture
Separate package builds avoid accidental workspace feature unification. The native consensus-only-perf-test mode is the paper artifact's VM-bypass performance mode; its native mempool skips VM admission validation. This must be declared in all comparison manifests. Native BLS consensus authentication, authenticated transport, payload handling, leader reputation and repair remain native. The artifact performance feature also selects FakeAptosDB: transaction/history maps are in memory, with a wrapped RocksDB used for genesis and remaining operations. Native default DAG configuration disables QuorumStore and carries direct authenticated transaction payloads. These are original paper-mode choices, not adapter storage replacements. Do not describe this as a full Aptos VM benchmark.

Remote placement
Set SHOAL_BENCHMARK_VALIDATOR_IPS to the comma-separated private IPv4 addresses in replica-index order when generating genesis. Each validator's native peer endpoint is its own private IP TCP8000; REST is 127.0.0.1:8001 and inspection is 127.0.0.1:8002. This binds discovery addresses in the native genesis ceremony. The other generated public/VFN listeners are not used for inter-validator consensus and must not be exposed by security groups. Keep controls and ingress behind host-local access/SSH tunnels. Distribute each validator's config/identity/genesis only to its assigned host and preserve or rewrite configuration filesystem paths before launching. Genesis and on-chain addresses must remain identical across validators. A remote fixture launcher must validate all advertised addresses before starting workloads.

Why not upstream forge local-swarm
The pinned Forge CLI hardcodes consensus_only_realistic_env_max_tps and overrides local ingress to MaxLoad with backlog5000. More seriously, LocalFactory::launch_swarm ignores the suite's genesis and node-configuration callbacks. Its default local genesis selects Jolteon, so invoking that command is not evidence of a Shoal++ run. Our separate shoal-fixture binary uses the same native genesis builder with an explicit DAG on-chain configuration. It does not change protocol algorithms or silently reuse Raptr.

Remaining acceptance gates
Compile the fixture on the Linux build host; inspect generated genesis/on-chain configuration and actual ShoalppBootstrapper startup; validate the implemented common finite arrival, exact payload-verified contiguous output and native traffic ledgers; run n4 healthy/disruption/zero/unfinished and n7 before distributed campaigns. Do not promote native REST VM completion or a descriptor-only ordering timestamp to the common materialization endpoint.

Prepared observer/fault scopes
The native TcpSocket records successful underlying reads/writes (including Noise framing/authentication); external REST ingress is outside that validator TCP boundary. Snapshots every 10 ms preserve actual host-local window sample timestamps. A 24-byte MAP_SHARED sidecar exposes exact totals recorded by native successful-I/O counters through confirmed suspension, after waitpid(WUNTRACED) confirms every validator is stopped. The controller includes writes recorded after the latest periodic snapshot, but excludes syscall completions not yet recorded at suspension and shutdown traffic; these are not kernel-wire totals. Optional BLS12-381 synchronous CPU guards cover signing, individual verification and aggregate verification, with signing preimage serialization included and inner verification serialization excluded. Client Ed25519 and Noise authentication are separate. Optional semantic omission gates only the configured faulty author's native Node/CertifiedNode publication units and repair replies containing its nodes. A repair reply can also bundle other nodes: the entire native unit is omitted, never rewritten. Control-only node certificates and honest custody remain unchanged. Native local functional fixtures now verify complete output/traffic accounting and actual semantic omission.17 Linux adapter tests pass. Detailed-observer overhead controls remain unvalidated for Shoal.

The local launcher scripts/baselines/shoal.py performs exact binary/patch/ABI checks, explicit DAG genesis, finite signed workload preparation, loopback REST readiness, independent origin schedules, owned process pause/resume, exact output prefix validation, cohort reduction and traffic accounting. --plan-only archives a non-executed contract. The collector independently verifies signed native BCS identities/content, and malformed/unplanned application content receives no useful credit while preserving every actual output ordinal. Formal comparison eligibility remains false until native execution acceptance.

Completed build and local runtime prerequisites
Attempt5 produced both the native aptos-node and shoal-fixture Linux ARM64 executables. Exact binary/ABI/source/lock/resource receipts are summarized in benchmarks/results/shoal-native-build-2026-10-19.json. The strict source guard also passed after compilation. This establishes compilation, not finite-cohort execution acceptance.
The first native startup attempt exposed inherited container download proxies: Aptos's TCP transport consults the HTTPS proxy even for native peer connections, and local generated discovery addresses can be 0.0.0.0. The launcher now removes all case variants of HTTP_PROXY/HTTPS_PROXY/ALL_PROXY from validator children, sets both NO_PROXY forms to *, and uses an explicit proxy-free REST opener. Build download proxy settings remain outside those children. Regression tests cover case variants and real loopback HTTP requests under poisoned proxy settings. Native source and executables did not change.
The owned VM's zram swap reactivated after an initial swapoff; the initiating service trigger was not established. A runtime mask of only dev-zram0.swap plus explicit swapoff kept the kernel swap table empty across independent checks. The local runner now rejects any enabled swap before genesis and records the kernel swap table again at final collection, failing classification if it is enabled. These VM-only controls do not change the user's default VM. Actual runtime acceptance remains a separate recorded gate.
