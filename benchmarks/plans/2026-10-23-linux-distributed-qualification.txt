2. Common placement and host-local lifecycle

Add a common-artifact recipe/publication route to deployment_prepare.py and a
common-node supervisor with per-core lifecycle adapters. Existing recipes and
remote_deployment.py still bind root src/*.rs and launch delugi-replica. Bind
the complete common closure, one executable hash and explicit --protocol.

Reuse strict SSH inventory, saved inventory import, resource enforcement and
PID/start/session ownership. For the first deployment profile require four
distinct hosts and validated private peer addresses. Keep controls on loopback
through pinned SSH tunnels; distribute each host's own secret key plus public
committee material. Allocate fresh, owned database directories.

Generalize mechanisms already exercised by remote_native.py's Shoal path:
immutable run nonce + plan/config/artifact hashes; all-host preparation before
arm; readiness revalidation; host-local epochs; abort tombstones for late
workers; concurrent cleanup before joining blocked workers. Keep core readiness,
start and freeze behavior in their respective adapters, without a universal
consensus API. Shared mechanism code must not branch on consensus message types.

Each host establishes its monotonic workload epoch after the barrier. Retain
requested/actual phase transitions and dispatch/skew evidence separately.
Delugi currently converts controller start_unix_us via its local wall clock
(run_sustained.py:383-386, process.rs:1578); replace this dependency with a local
relative arm/start path. Raptr's local controller currently supplies one shared
monotonic epoch (run_raptr_shared_local.py:570); the remote path needs one per
host. All workload and fault offsets are relative to the appropriate host epoch.

Keep current launch guards until the new path validates the full contract:
Raptr config.rs:115 requires loopback; run_sustained.py:706 rejects remote common
receipts; :278 separately rejects remote shared RocksDB. Replace those guards
with explicit validated deployment capability, not unconditional permission.

Reuse runtime_evidence.py's bounded, hashed transfer. Extend its allowlist for
common-node ready/arm/freeze/final/profile/request/output evidence, excluding
keys and databases. Every start, status, freeze, export and cleanup operation
needs a finite timeout. Failed transfer retains partial local evidence and
remote evidence, fails acceptance and triggers independent cleanup attempts
on every contacted host. Only confirmed empty owned groups count as cleanup.

Tests: partial upload/startup, readiness loss, stale/replayed arm, lost arm reply,
timeout, controller interruption, abort before process creation, late worker,
paused descendant, reused PID, hanging/truncated/tampered export and cleanup

3. Sustained Raptr and matched evidence

Keep the finite schema and its accepted fixtures replayable. Add a versioned
sustained experiment schema: total rate/origin schedule, useful bytes, actual
serialized bytes, warmup/measurement/drain, bounded preparation/storage,
host-local epochs, explicit offer outcomes and boundary receipts. Extract only
generic rate arithmetic and evidence mechanisms into shared code. Native BCS
transactions, identity validation, batch cutting, proofs and repair remain
inside core/raptr.

The current Python runner permits only 5,000 requests per origin; the node caps
the committee at 100,000 prepared requests/128MiB and measurement/drain at 60s
each. workload.rs:203-267 precomputes transactions; :399-463 retains and clones
rows/output at freeze. factory.rs:115 buffers serialized output, and :277 sets
a fixed 180s end guard before arming. Raising those constants alone does not
provide multi-minute sustained qualification.

Use bounded preparation chunks or a pre-generated sharded spool, independent
shared_mempool::Worker arrivals, nonblocking admission and streamed authenticated
evidence. Derive the harness end guard from the declared lifecycle envelope;
preserve native protocol timer multipliers. Record preparation lag as scheduled
arrival delay and unoffered work, rather than adapting offered load to service.

Record intended, offered, admitted, rejected, completed and unfinished work
independently. The current cutoff-crossing enqueue attempt returns without an
outcome (workload.rs:75-87), while offered is inferred from admitted+rejected.
Preserve rejection of late admission; record the attempt and its late/cancelled
outcome explicitly. Reconcile every intended identity, including unoffered and
unfinished work. Never grant useful credit to output predating admission.

Normalize verified native evidence into cohort_store.py/CohortDatabase and
cohort_metrics.py. Preserve exact native batch identities and raw output order;
count unique useful goodput separately. Use half-open origin-local measurement
cohorts, warmup carry-in, late drain completions, censored tails and backlog
subwindows. Validate identity/prefix agreement across replicas without subtracting
their clocks. Disable remote all-correct latency; retain final all-correct
completion membership. Raptr's current reducer assumes one epoch and compares
freeze with controller time (:1024-1035), as well as subtracting replica clocks
for all-correct latency (:1083-1093); both assumptions need replacing.

Add explicit stage availability and local batch/proposal/certification/
materialization observations, keyed by native identities. own_batch_ready_us
currently remains null. Do not infer it from commit/output or require own batch
readiness before legitimate inline output. Primary latency remains successful
origin-local admission to payload-verified contiguous application output.

Add signed counter snapshots at matching measurement boundaries. Raptr currently
freezes TCP counters before shutdown; Delugi quiesces and drains before final
counters. Report measurement-window, drain and shutdown traffic separately;
validate the same selected boundary before comparing. Scope remains successful
authenticated TCP-stream writes including framing/authentication/ACK overhead,
excluding TCP/IP headers and kernel retransmission.

Tests: exact rate allocation/fractional intervals/overflow; queue saturation and
cutoff crossings; empty/zero-output/unfinished cohorts; warmup carry-in; large
streamed journals with bounded memory; missing/duplicate shards; disk exhaustion;
tampering; duplicate/unknown output; per-host clock-offset invariance; traffic
boundary parity. Add sustained-stage tests without changing native policy.

5. Four-host pilot and performance qualification

After remote wiring/local Linux checks pass and the user authorizes execution,
run the four-host engineering pilot on the exact target artifact and profiles.
Start unshaped, require complete startup/output/freeze/transfer/cleanup evidence,
then run 4k tx/s and below/near/above-saturation schedules with repeats and a
multi-minute soak. Determine saturation empirically and preserve rising backlog,
rejections, unfinished tails, stage timings, traffic and memory growth.

Enforce and record aggregate whole-replica CPU/memory/swap/storage budgets,
including Tokio/Rayon/network/RocksDB workers; equal executables do not imply
equal executor topology. Use compatible declared storage completion for matched
runs: fresh WAL-enabled sync=false Written databases, with retained in-memory
state. Delugi memory acceptance remains a separate profile. Record all actual
queue/frame/window limits and native worker/cache/background settings.

Calibrate added delta10ms independently of protocol Delta100ms and native
multipliers. Require unshaped baseline, directed edge/role identity, raw active
RTT evidence and cleanup verification before accepting shaped protocol results.
The previous VM's rejected 25.78-29.37ms added RTT remains rejected against
20+/-5ms; it predicts neither acceptance nor failure on Alibaba.

Keep fixed Delugi 256KiB batch payload separate from proposal/frame profiles.
Raptr's per-batch byte setting is unenforced; its nominal 200-batch pull can
admit 201. Retain these native behaviors and report effective limits. Any
byte-splitter/cap policy change needs an explicit named variant and separate
conformance decision. It is not required to make the first pilot deployable.

After n4 qualification, requalify n7 then n31 on the common artifact before
publishing scale results. Multiple faulty identities and repeated failures
require their own campaign evidence. Restart recovery becomes relevant only
when crash/restart experiments enter the claims.

Acceptance state transitions

Functional: exact artifact/profile passes protocol, output and cleanup controls.
Deployment: all hosts verify placement/readiness/epochs, complete evidence
transfer and confirmed cleanup, including tested lifecycle failures.
Performance: matched workload/cohorts, effective resources/storage, traffic
boundaries, timing controls and repeated stable-load/overload evidence pass.
Advance each status independently; publication or build success advances none.
